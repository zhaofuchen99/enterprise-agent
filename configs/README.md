# configs/

| 文件 | 用途 | 生成方式 | 入版本库 |
|---|---|---|---|
| `rag_user_dict.txt` | jieba 业务词典（**产物**）。每行一个词，无注释、无词频 | `make dict` | ✅ 是 |
| `rag_terms.txt` | 手工业务术语表（**输入**）。复合词，可带 `#` 注释 | 手工维护 | ✅ 是 |
| `rag_stopwords.txt` | 停用词，每行一个 | 手工维护 | ✅ 是 |

配置项 `RAG__USER_DICT_PATH` / `RAG__STOPWORD_PATH` / （术语表的路径写在
`scripts/gen_dict.py` 里，它不是运行时配置）分别指向它们，都是一对普通默认值，
不必写进 `.env`。

## 词典为什么分成"输入"和"产物"两个文件

词典由三个来源拼成（`scripts/gen_dict.py`）：业务库维度表取值、`schema_catalog.yaml`
的指标名与别名、以及 `rag_terms.txt` 里手工维护的复合词。

前两个来源是**自动**的——库里加了产品线、目录里加了指标，词典必须跟着变，
否则会漏词且**没有任何东西会报错**（表现只是"某个产品的检索忽然变差了"）。
所以词典不能手写，只能生成。第三个来源是自动提取覆盖不到的复合术语
（如「渠道折扣」「归口管理部门」），必须手写，故单列成 `rag_terms.txt`。

**两份都提交**：`rag_user_dict.txt` 虽然是产物，但它是**检索契约**的一部分——
查询侧与入库侧必须用同一份切分。新克隆的仓库若缺了它，`Tokenizer` 会退化成
通用分词并打一条 warning，而已入库 chunk 是用带词典的分词建的，
两边从此对不上（表现为"某些查询永远召回不到东西"）。
这与语料（`data/corpus/`，gitignore）的取舍不同：语料可以随时重建，
词典一旦不一致，症状不指向词典。

## 改词典的纪律

- **唯一写入方是 `make dict`**（前置：`make up` + 业务库已灌数）。
  产物是生成的，手改会被 `scripts/gen_dict.py --check` 与
  `app/tests/tools/rag/test_tokenizer.py` 里的产物断言同时挡下。
- 生成器**逐条回读产物自检**：加载后仍切不出自己的词条 → 非零退出；
  手工表里通用词典本就切得对的死条目 → 非零退出。
  理由与语料缺陷注入同一条（CLAUDE.md 约定 11）：**清单里写了不是证据，产物生效才是**。
- **产物文件里不能写注释**——jieba 的 `load_userdict` 会把匹配不上
  词频/词性后缀的整行当成词条加进去（实测 `jieba.get_FREQ()` 返回 1）。
  出处写在本文件、`scripts/gen_dict.py` 与 `rag_terms.txt` 里。
- 词典变更必须重跑 RAG 检索回归集（详设 11.6.2），因为切分结果直接改变检索结果。

## 关于停用词表为空

`rag_stopwords.txt` 保持为空是**刻意**的，不是漏做：11.6.1 把停用词过滤列为可选步骤，
理由是 BM25 的 IDF 本身就会抑制高频词。真正的停用词表要等语料冻结后按实际词频
统计生成，现在硬塞一份通用表反而会把业务词误杀。

词表扩容后必须验证历史 chunk 仍可被召回、无需重算稀疏向量（已在
`test_tokenizer.py::test_expanding_vocabulary_keeps_old_chunks_retrievable` 覆盖）。
